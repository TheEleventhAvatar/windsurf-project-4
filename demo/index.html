🎬 Demo: API Success ≠ Browser-Visible Success

A minimal, reproducible demonstration showing why autonomous agent evaluations that only check API responses miss real end-to-end failures visible to users in the browser.

The Problem

Autonomous workflows driven by agents typically:

  • Make API calls and check response codes (200, 201)
  • Assert that fields in responses indicate success
  • Assume the work is complete and proceed

But in distributed systems with eventual consistency, API success doesn't guarantee immediate observable UI state change.

What This Demo Shows

✅ API-Level Test

Test: Vitest (mock backend)

Result: PASS

All API responses return success. Canonical backend state shows PR merged and issue closed.

❌ Browser-Level Test

Test: Playwright (real browser)

Result: FAIL

UI shows stale state immediately after API returns success. Webhook delay causes mismatch.

Agent checking API only: "Success, moving on!" User looking at browser: "Why is the PR still showing as Open?"

2. Run API-only Test (PASS)

npx vitest run tests/demo-api.test.ts

3. Run Browser Test (FAIL)

npx vitest run tests/demo-browser.test.ts

4. Run Visual Demo

npx ts-node demo/visual-demo.ts

The visual demo opens a live browser and captures screenshots showing the stale UI.

Why This Matters

For autonomous agent workflows, this demonstrates a critical gap in evaluation approaches:

  • API-only evals are insufficient — They check response codes and object fields, but miss eventual consistency delays.
  • Browser-level evals are necessary — They catch what users actually see, including stale states and race conditions.
  • Real production systems exhibit this — Webhooks, caches, and distributed architecture make this a common edge case.
  • Agents need full-stack validation — Before proceeding after a workflow step, agents should validate both API success AND observable UI consistency.
